A self hosted server is full of secrets in plain files: database passwords in
`.env` files, private SSH keys, registry logins, tunnel tokens. Encryption at
rest does not help while the server is running. File permissions are the lock.

## Why it is dangerous

Linux permissions say who may read a file: its owner, its group, and everyone
else ("other"). A file with mode `0644` is readable by every account on the
machine, including the unprivileged users that web servers, cron jobs and
compromised apps run as.

Secrets end up world readable in ordinary ways:

- A platform writes app `.env` files with default permissions on every deploy.
- A private key is copied with `cp` and keeps a loose mode, or is created by a
  tool that does not care.
- `docker login` stores registry credentials in `~/.docker/config.json`.

Environment variables are not much better. Docker's Compose documentation
warns that secrets passed as environment variables are often available to all
processes, are hard to track, and can end up in logs when debugging. They also
appear in `docker inspect` output.

## What an attacker can actually do

The first foothold on a server is often a low privileged one: a bug in one web
app gives a shell as that app's user. If that user can read another app's
`.env`, the attacker now has that app's database password, its API keys, its
mail credentials. If it can read a platform's SSH key folder, they have keys
to every server the platform manages. One weak app becomes every app.

No privilege escalation is needed. Reading a file you are allowed to read is
not an exploit.

## See it on your own server

These commands print owner, group and mode. They never open the files, which
is the same rule stackward follows.

```sh
# .env files under a platform data root (Coolify uses /data/coolify)
sudo find /data -name '.env' -printf '%m %u:%g %p\n' 2>/dev/null

# private keys in home directories and root's
sudo find /home /root -name 'id_*' ! -name '*.pub' \
  -printf '%m %u:%g %p\n' 2>/dev/null
sudo find /home /root /etc \( -name '*.pem' -o -name '*.key' \) \
  -printf '%m %u:%g %p\n' 2>/dev/null

# registry credentials
sudo find /home /root -path '*/.docker/config.json' \
  -printf '%m %u:%g %p\n' 2>/dev/null
```

Read the first number: `600` (owner only) or `640` (owner and one group) is
what you want. A last digit other than `0` means every user can read it.

## What the fix changes

- **`chmod 600`** for private keys, `.env` files and credential files, so only
  the owner can read them. `chmod 700` for directories that hold keys.
- **Keep the owner right.** `600` owned by the wrong user locks out the
  service that needs the file.
- **Use secret files instead of environment variables** where the app
  supports it (Compose `secrets:` mounts a file the app reads), so the value
  does not show up in `docker inspect` or process listings.
- **Use a credential helper** for `docker login` instead of a plain file.
- **Watch for regressions.** If a platform resets permissions on every deploy,
  a timer that reapplies them is a workaround until the platform fixes it.

## What the fix can break

- A service that runs as a different user than the file's owner can no longer
  read it. Some platforms need their main `.env` readable by a specific group
  so their own container can start; plain `600` breaks them. Check what the
  platform documents before tightening its files.
- Switching to Compose secrets needs app support for reading a file
  (`*_FILE` variables, for example).

<Aside type="caution" title="Never paste the contents">
When you ask for help, share the permission line, not the file. stackward
reads only metadata of secret files and redacts secret shaped values from
everything it prints.
</Aside>

should be world writable ([SEC-007](/stackward/checks/sec-007/)), because the
