Most break ins do not use clever new attacks. They use known holes that a
patch fixed months ago, on servers that never got the patch, or got it and
never restarted.

## Why it is dangerous

Three separate things have to be true for a fix to protect you:

1. **The update is installed.** On Ubuntu, the `unattended-upgrades` package is
   installed by default and applies security updates automatically when
   `/etc/apt/apt.conf.d/20auto-upgrades` enables it. On Debian you install
   and enable it yourself; its default configuration installs security updates
   and not new features.
2. **The patched code is running.** A new kernel only runs after a reboot.
   Long running services keep using the old copy of a library until they
   restart. Ubuntu's unattended upgrades does not reboot unless you set
   `Unattended-Upgrade::Automatic-Reboot "true"`; the default is false.
3. **The release still gets updates.** Ubuntu LTS releases get five years of
   standard security maintenance. Debian releases get three years of full
   support and two more of Long Term Support. After that, nothing new arrives,
   however often you run `apt upgrade`.

## What an attacker can actually do

When a serious vulnerability in a common component is published, scanners
start looking for unpatched versions soon after. A server that is a few weeks behind
on a public facing package, or still running last year's kernel because nobody
rebooted, is exactly what they look for. A release past its end of support is
worse: every hole found from then on stays open forever on that server.

The attacker does not need to know you exist. They need one version string
that matches a public advisory.

## See it on your own server

Are automatic updates on, and when did they last run?

```sh
cat /etc/apt/apt.conf.d/20auto-upgrades
systemctl status apt-daily-upgrade.timer --no-pager
ls -l /var/log/unattended-upgrades/
```

Look for `APT::Periodic::Unattended-Upgrade "1";` and a recent log.

Is a reboot pending, and is the running kernel the newest installed one?

```sh
ls -l /var/run/reboot-required
cat /var/run/reboot-required.pkgs
uname -r
ls /boot/vmlinuz-*
```

Which updates are waiting (a simulation, it installs nothing)?

```sh
apt-get -s upgrade | grep -i security
```

Which release is this, and when does its support end?

```sh
cat /etc/os-release
```

Compare with the Ubuntu release cycle page or the Debian releases page in the
sources below.

<Aside type="caution" title="Debian 12 is already in LTS">
Debian 12 (bookworm) reached the end of its regular support on 2026-07-11 and
is now covered by Debian LTS until 2028-06-30. LTS covers fewer packages than
regular security support; plan the move to Debian 13.
</Aside>

## What the fix changes

- **Turn on unattended security upgrades**, so holes in packages you use
  close within a day without anyone logging in.
- **Decide on reboots.** Either set an automatic reboot window
  (`Automatic-Reboot "true"` with `Automatic-Reboot-Time`), staggered across
  servers, or put a weekly manual reboot in your calendar. A pending reboot
  that lasts weeks means the kernel fix is on disk and not in effect.
- **Upgrade releases before they end.** Plan the move to the next LTS while
  the current one still has a year or more of support.

## What the fix can break

- **Automatic reboots** take every service down for a minute. Containers
  without a restart policy stay down afterwards. Set `restart:
  unless-stopped` and test a reboot on a quiet day.
- **An update that changes behaviour** can break an app, although security
  pockets keep such changes rare. Keep backups, and watch the
  unattended-upgrades log.
- **Release upgrades** are real migrations: new major versions of system
  packages, sometimes of Docker's dependencies. Rehearse on a copy first.

## Disk, time, logs and backups

A server can fail quietly without any attacker. Docker's default `json-file`
log driver has no size limit unless you set `max-size` (its default is -1,
unlimited), so a noisy container can fill the disk
([DKR-031](/stackward/checks/dkr-031/)). journald may use 10 percent of the
filesystem, capped at 4G, unless you set `SystemMaxUse=`
([LOG-001](/stackward/checks/log-001/), [LOG-003](/stackward/checks/log-003/)),
and it keeps the journal across reboots only when `Storage=persistent` is in
effect or `Storage=auto` finds `/var/log/journal`
([LOG-005](/stackward/checks/log-005/)). The audit also looks at free space
on `/`, `/var` and the Docker root ([SYS-005](/stackward/checks/sys-005/)),
proxy access log rotation ([LOG-002](/stackward/checks/log-002/)) and whether
the clock is synchronized ([SYS-004](/stackward/checks/sys-004/)).

Two more checks are about being able to recover and notice: a metrics agent
([LOG-004](/stackward/checks/log-004/)) and backups of the platform's own
database and host level backup tools
([BAK-001](/stackward/checks/bak-001/), [BAK-002](/stackward/checks/bak-002/)).
They only report what exists; whether a backup restores is something only a
restore test shows.

Versions matter too: the audit reports a distribution it is not tested on
([SYS-001](/stackward/checks/sys-001/)), a Docker Engine release line past
upstream support ([DKR-034](/stackward/checks/dkr-034/), dates from
endoflife.date) and infrastructure containers on `:latest` or no tag
([DKR-032](/stackward/checks/dkr-032/)).
